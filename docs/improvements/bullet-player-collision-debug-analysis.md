# Анализ проблемы: q_players всегда возвращает 0 игроков

## Проблема
В системе `handle_bullet_player_collision` запрос `q_players` всегда возвращает 0 игроков, хотя игроки должны существовать в игре.

## Текущий запрос
```rust
q_players: Query<(Entity, &PlayerNo, &Transform, &Children), With<PlayerNo>>
```

## Возможные причины

### 1. Компонент `Children` отсутствует или удалён
**Проблема:** Запрос требует компонент `Children` явно. Если у игрока нет дочерних элементов или компонент был удалён, запрос не вернёт эту сущность.

**Почему это может происходить:**
- В Bevy компонент `Children` добавляется автоматически при использовании `add_child()`
- Если все дочерние элементы удалены, компонент `Children` может остаться пустым, но не удалиться автоматически
- Однако, если компонент был явно удалён или никогда не добавлялся, запрос не найдёт сущность

**Проверка:** В коде создания игрока (строка 221 в `player.rs`) используется `commands.entity(tank).add_child(shield)`, что должно добавить компонент `Children`. Но если щит удаляется до выполнения запроса, компонент может быть проблемой.

### 2. Порядок выполнения систем
**Проблема:** Система может выполняться до того, как игроки заспавнены.

**Анализ:**
- `auto_spawn_players` выполняется в `GameplaySet::Spawning`
- `handle_bullet_player_collision` выполняется в `GameplaySet::Collision` после `BulletMovement`
- Порядок: `Spawning` → `Movement` → `Combat` → `BulletMovement` → `Collision`

**Вывод:** Порядок выполнения должен быть правильным, игроки должны существовать к моменту выполнения системы.

### 3. Игроки деспавнятся до выполнения системы
**Проблема:** Игроки могут быть удалены другой системой до выполнения `handle_bullet_player_collision`.

**Проверка:** Нужно убедиться, что нет систем, которые удаляют игроков раньше.

### 4. Запрос слишком строгий
**Проблема:** Требование `&Children` может быть слишком строгим. Если компонент отсутствует, запрос не вернёт сущность.

## Решения

### Решение 1: Сделать `Children` опциональным
Использовать `Option<&Children>` вместо `&Children`:

```rust
q_players: Query<(Entity, &PlayerNo, &Transform, Option<&Children>), With<PlayerNo>>
```

**Преимущества:**
- Запрос вернёт игроков даже если у них нет дочерних элементов
- Можно обработать случай отсутствия `Children`

**Недостатки:**
- Нужно обрабатывать `Option` в коде

### Решение 2: Разделить запрос на два
Сначала найти игроков без требования `Children`, затем получить `Children` отдельно:

```rust
q_players: Query<(Entity, &PlayerNo, &Transform), With<PlayerNo>>,
// Затем получить Children отдельно через commands.entity(player_entity).get::<Children>()
```

**Преимущества:**
- Гарантированно найдёт всех игроков
- Можно получить `Children` опционально

**Недостатки:**
- Требует дополнительных запросов к World

### Решение 3: Использовать отдельный запрос для проверки дочерних элементов
Использовать `Query<Entity, (With<PlayerNo>, With<Children>)>` для проверки наличия дочерних элементов:

```rust
q_players: Query<(Entity, &PlayerNo, &Transform), With<PlayerNo>>,
q_players_with_children: Query<&Children, (With<PlayerNo>, With<Children>)>,
```

**Преимущества:**
- Найдёт всех игроков
- Можно проверить наличие дочерних элементов отдельно

**Недостатки:**
- Более сложная логика

### Решение 4: Добавить логирование для диагностики
Добавить логи, которые покажут:
- Сколько игроков в запросе без требования `Children`
- Есть ли у игроков компонент `Children`
- Когда игроки создаются и удаляются

## Рекомендация

**Рекомендуется использовать Решение 1** - сделать `Children` опциональным. Это самое простое и надёжное решение, которое гарантирует, что все игроки будут найдены, независимо от наличия дочерних элементов.

## План действий

1. Изменить запрос на `Option<&Children>`
2. Обновить код обработки для работы с `Option`
3. Добавить логирование для проверки количества игроков
4. Протестировать, что игроки теперь находятся в запросе
